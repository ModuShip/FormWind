Performance

A styling layer must not make an application feel slower. tools/FormWind.Benchmarks builds the same form with plain WinForms, FormWind, Krypton Toolkit and MaterialSkin.2, then measures time, memory and GDI/USER objects.

In short (200 controls, primary screen)

Opening a form: FormWind 185–228 ms, plain WinForms 236 ms, Krypton 346 ms, MaterialSkin 365 ms. Switching between light and dark: FormWind 16–29 ms. FormWind uses as many GDI/USER objects as plain WinForms, and its counts stay constant over 500 open/close cycles.

  • Repaint is Form.Refresh(). Tw* controls and AutoStyle repaint as fast as plain WinForms; classes on standard controls cost more because of corner Regions and painted borders.
  • Hover is one WM_MOUSEMOVE or WM_MOUSELEAVE with the paints it causes. MaterialSkin does most of its hover work later, in an animation timer, so its number does not include it.
  • GDI / USER objects per form: FormWind adds no GDI objects; Tw* controls that wrap a native box have one extra window each.
  • Cold start to the first painted form: FormWind 423–498 ms, plain WinForms 323 ms, MaterialSkin 524 ms, Krypton 693 ms. FormWind adds five assemblies and about 6 MB of private memory.

Bottlenecks fixed

Profiling with dotnet-trace found five problems, now fixed. Shadows and frames were repainted without checking the invalid region, padding changed twice on every refresh, text was measured again on every refresh, and fonts were scaled twice when a form moved to a screen with another DPI.

Time grows linearly with the number of controls. Adding controls later grows from 250 to 2000 controls at the same rate as WinForms itself (FormWind ~9x, WinForms ~12x); use SuspendLayout for bulk adds. FormWind runs the parent's layout once while styling a control (before, each font, padding and size assignment triggered its own layout: 2000 controls 5.8 s → ~4.1 s). At ~60 theme switches per second color transitions overlap, every control ends on its target color and the handle count does not grow; with 200 animated controls the frame rate drops to ~10 fps. Thresholds are time per control and growth ratios, not fixed milliseconds.

Long-running use

SoakTests opens a form full of controls that FormWind subclasses or hooks (dark ListView and TreeView, RTF, DropDownList, DateTimePicker, disabled ListView and ComboBox, tooltips, PropertyGrid) again and again. Each round switches the theme, sets the application's own theme, recreates handles and closes the form; a provider attached by hand and TwAutoTheme are tried separately. Over 300 rounds (net9) GDI stays 62→62, USER 37→37 and managed memory at ~4.3 MB; a round takes as long in the second half as in the first, and every form and provider except the last round's is collected.

Method

  • Each scenario repeats the same six roles (label, primary button, secondary button, text box, card, check box) in a FlowLayoutPanel on a 1200 × 900 borderless form, at 50, 200 and 500 controls.
  • Each scenario and size runs in its own process, so JIT, global palettes and process-wide GDI counters do not mix. Two forms are opened and closed before the warm measurements; values are medians with p90.
  • Hover uses real mouse messages; --other-dpi opens the form on a monitor where it receives WM_DPICHANGED.
  • Measured on 2026-10-14 on an Intel Core i5-12450HX, Windows build 26200, .NET 8.0.11, 120 DPI.

One machine and one run: values vary by about ±10–15%, though the order did not change between runs. The scenarios do not look identical; each library uses its own components (for example KryptonForm and MaterialForm).

Run it yourself

dotnet build tools/FormWind.Benchmarks -c Release
tools/FormWind.Benchmarks/bin/Release/net8.0-windows/FormWind.Benchmarks.exe                 # all scenarios, ~15 min
tools/FormWind.Benchmarks/bin/Release/net8.0-windows/FormWind.Benchmarks.exe --quick --only formwind,krypton --sizes 200

Results are written to artifacts/benchmarks/results.json and results.md. The full report, with every size and the other-monitor runs, is in docs/benchmarks.md (Turkish).
